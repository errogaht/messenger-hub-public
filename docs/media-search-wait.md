# Голосовые, файлы, поиск и ожидание

Messenger Hub предоставляет общий интерфейс для всех подключений. Провайдерские
особенности остаются в адаптерах; аккаунты, чаты и права не смешиваются.

## Голосовые и аудио

`messenger_history` автоматически ставит аудиовложения в очередь Palatine ASR (с HUB-019 — для всех каналов, без fallback).
Используется тот же приватный ключ Hub с правами `gpt-6-luna` и `gpt-4o-transcribe`.
Endpoint и multipart-формат взяты из проекта Voice Input:
`POST /backend-api/transcribe`, Codex User-Agent, без поля model и без переключения
на платный внешний ASR endpoint. Текстовая модель для стиля и распознавание аудио —
разные операции, хотя используют один ключ.

При готовой транскрипции `message.text` содержит исходную подпись и явно помеченную
`[Транскрипция аудио]`; `sourceText` сохраняет исходный текст провайдера.
В `attachments[].transcription` отдельно передаются статус и текст.
Внутренний агент стиля получает этот нормализованный текст через обычную историю.
Существующие тексты и сегменты архива МТС сохраняются, повторный ASR звонков не запускается.

На всю страницу действует один бюджет ожидания ASR: 15 секунд по умолчанию.
`audioWaitMs: 0..30000` меняет его для конкретного чтения. По истечении бюджета
страница возвращается полностью, а аудио имеет статус queued/running. Работа
продолжается внутри Hub; `messenger_transcription_status({fileId})` возвращает
результат. Повторное чтение использует кэш. Ошибка одной записи не скрывает другие.

Кэш привязан к исходному файлу и SHA-256 содержимого. Два одинаковых аудиофайла
не требуют второго ASR-запроса. Ошибки не повторяются бесконечно: явный
`messenger_transcribe_media({fileId,retry:true})` повторяет failed/interrupted.
После перезапуска незавершённая задача помечается interrupted. Это предотвращает
незаметные повторные загрузки, если результат прошлого запроса неизвестен.

Состояния: not_started, not_requested (видео), queued, running, ready, failed,
too_large, interrupted. Ошибки возвращаются короткими кодами без ключей и тел аудио.
Распознавание является машинной транскрипцией, а не доказательством точности каждого
слова или личности говорящего; timestamps/диаризация этим endpoint не возвращаются.

## Видео и изображения

Видео не скачивается и не распознаётся автоматически. Агент явно вызывает
`messenger_transcribe_media({fileId,waitMs:0})`, получает состояние и проверяет его
через `messenger_transcription_status`. Hub скачивает видео, извлекает аудиодорожку
ffmpeg и распознаёт через тот же ASR. Если аудиодорожки нет, возвращает no_audio_track.

Изображения Hub перечисляет и скачивает. Их содержимое изучает основной агент.
Стилевой агент не делает выводов по непроверенной картинке или подписи к ней.

## Вложения и скачивание

Каждое вложение истории/поиска имеет:

- прежний provider `id` для совместимости;
- `fileId` — непрозрачный UUID Hub;
- kind, filename, mimeType, size (null, если провайдер не сообщил);
- downloadUrl и описание требуемой авторизации;
- состояние транскрипции, когда применимо.

`messenger_file_download({fileId})` самостоятельно находит подключение, чат,
сообщение и способ скачивания. Возвращает приватный локальный path, filename,
фактический размер, SHA-256 и URL. Большой base64 не попадает в контекст агента.
Для клиента на этом же компьютере пригоден локальный path. Для HTTP-клиента
`GET http://127.0.0.1:8792/files/UUID` требует его scoped Bearer в заголовке.
URL не публичный и не содержит токен. Знание UUID не даёт доступ к чужому файлу.

Старый `messenger_attachment` сохранён (base64, до 25 MiB). Новый путь Telegram и
WhatsApp поддерживает скачивание в файл до 256 MiB; адаптеры с прежним base64
контрактом, включая текущий Bitrix/MTS, сохраняют собственный предел 25 MiB.
Пути Telegram проверяются внутри разрешённого media root. Относительные пути
GOWA разрешаются строго внутри `statics/media`, а не относительно cwd Hub.
Идентификатор сообщения ответа GOWA и фактический размер проверяются, если доступны.

`downloadDiagnostic` описывает текущий отказ получения оригинала. После нового
успешного скачивания (проверены размер, приватный путь, SHA-256 и сохранение файла)
или успешного обращения к допустимому непустому кэшу это поле удаляется. Ошибки
и история транскрипции, сведения источника и другие audit-поля не удаляются.
Отсутствующий, пустой, слишком большой или выходящий за private root кэш остаётся
ошибкой; Hub не подменяет его успехом и не начинает скрытое повторное скачивание.

Если MCP transport явно закрылся, Hub перестаёт использовать именно это соединение.
Следующий отдельный вызов подключается заново; неудавшееся чтение или отправка
не повторяются внутри Hub. Общая ошибка `onerror` не закрывает живое соединение:
в нём может ещё выполняться отправка. Запоздавший close старого клиента не снимает
новое соединение. Права и точный маршрут проверяются перед кэшем и провайдером.

Telegram дополнительно получает сведения о файле без скачивания содержимого.
Для этого есть общий пятисекундный бюджет страницы и четыре параллельных запроса.
При недоступности необязательной метаинформации сохраняется известный маркер,
а `mediaMetadataIncomplete` явно отмечает неполноту. Web previews не являются файлами.

## Поиск

- `messenger_contacts({connectionId,query,limit,cursor})` — каталог/поиск контактов
  провайдера. Telegram и WhatsApp используют свои методы; для других плагинов
  доступен их каталог диалогов. Пагинация и ограничения отмечаются в результате.
- `messenger_contact_search` — отдельная адресная книжка людей Hub с псевдонимами
  и связями между каналами, созданная в HUB-002.
- `messenger_search_messages({connectionId,conversationId,query,limit,cursor})` —
  поиск сообщений в точном чате. Telegram/WhatsApp используют родной поиск.
  В Telegram upstream не имеет offset: адаптер расширяет окно и отдаёт страницы,
  максимум 1000 совпадений; `complete:false,next:null` обозначает предел окна.
  WhatsApp использует search+offset провайдера.

Если у другого плагина нет search, просматривается одна страница истории; next
позволяет продолжить. Поле coverage отличает native search от такого просмотра.
Уже распознанные голосовые также доступны в cachedAudioMatches. Это только
наблюдавшаяся и распознанная часть истории, не обещание поиска по всем голосовым
всего аккаунта. Неподходящие к запросу файлы не скачиваются ради поиска.

## Ожидание серии сообщений

`messenger_wait_for_settled_message` принимает:

```json
{
  "subscriptions": [
    {"connectionId":"telegram-main","conversationId":"123","afterMessageId":"456"},
    {"connectionId":"whatsapp-main","conversationId":"123@s.whatsapp.net"}
  ],
  "settleMs": 6000,
  "maxWaitMs": 50000,
  "direction": "inbound"
}
```

Дождётся новых входящих и паузы после последнего сообщения. `direction: all`
включает исходящие. `afterMessageId` — известное последнее сообщение чтения или
отправки; оно позволяет поймать ответ, уже пришедший до запуска ожидания.
Без него первая подписка начинается со снимка текущей истории.

Всегда передавайте возвращённый cursor в следующий вызов с теми же subscriptions,
settleMs и direction. Тайм-аут — нормальный результат event:false. В cursor
сохраняется незавершённая серия; следующий вызов продолжает ожидание.
Повтор одного курсора воспроизводит тот же результат. У каждого потребителя
свой курсор; они не забирают события из общей очереди Telegram.

Hub опрашивает только указанные чаты, по умолчанию раз в две секунды; одинаковые
одновременные запросы провайдера объединяются. Это long polling между агентом и
Hub, а не обещание push/webhook для всех провайдеров. Максимум 20 подписок на вызов
и 20 активных ожиданий. При потере непрерывности возвращает history_gap, при
слишком длинной непрерывной серии — burst_limit; их нельзя трактовать как отсутствие
сообщений. Для восстановления нужно явно прочитать историю и задать новую границу.

Результат события — сводка серии с readHistoryRequired:true. Затем основной агент
читает нужную историю для метаданных файлов и ASR; тяжёлая обработка не удлиняет
50-секундный предел ожидания.

## Хранение, пределы и откат

`media.root` хранит приватную SQLite-регистрацию, исходные файлы, тексты ASR и их кэш.
`readStore` (по умолчанию `<store>.reads`) хранит scoped cursor snapshots и результаты
ожидания. Это приватные данные, включая тексты сообщений. Каталоги 0700, файлы 0600.
Автоматического удаления/TTL пока нет; место на диске и резервные копии обслуживает
владелец. Не удаляйте кэши между обычными перезапусками.

Текущие конфигурируемые пределы: 2 ASR workers, очередь до 500 файлов, ASR timeout
60 секунд, аудио до 25 MiB и 20 минут, явное видео до 256 MiB и 60 минут. ffprobe
проверяет длительность, ffmpeg работает без shell и сетевых протоколов. Неподдержанный,
повреждённый, слишком большой или уже недоступный у провайдера файл получает
явное состояние ошибки; остальные сообщения возвращаются.

Для выключения автоматического ASR установите `media.autoAudio:false` и перезапустите
Hub. Явная транскрибация останется доступна. Для полного отката восстановите код и
config из backup HUB-003 и перезапустите сервис. Сохраните медиа, кэш, read cursors,
контакты и журнал отправок. При необходимости верните allowedModels существующего
ключа по сохранённому key-before-asr.json; ключ не перевыпускался. Voice Input,
провайдерские сессии и код WorkZone не изменялись.

HUB-019: МТС — только recording/metadata; full transcript/speaker uncertainty,
call limits и глобальный Palatine purpose описаны в [clerk-api.md](clerk-api.md).
